# Second Wind Games — Unity Build & Release Sandbox

세컨윈드게임즈의 **Unity 2D 빌드·배포·업데이트 사이클을 검증하기 위한 테스트 프로젝트**입니다.

게임 콘텐츠의 완성도보다는 개발 결과물이 실제 배포 환경까지 안정적으로 전달되는지 확인하는 데 목적이 있습니다. 최소한의 2D 플레이 환경을 유지하면서 버전 관리, 자동 빌드, 배포, 업데이트 및 롤백 절차를 반복해서 테스트합니다.

## 주요 목표

- Unity 프로젝트의 로컬 및 자동 빌드 검증
- 개발·스테이징·릴리스 환경별 설정 분리
- Git 브랜치와 빌드 버전의 연계 확인
- CI/CD 파이프라인 구축 및 반복 실행
- 빌드 산출물 배포와 설치 테스트
- 업데이트 및 롤백 절차 검증
- 빌드 실패 원인과 배포 이력 추적

## 테스트 범위

| 구분 | 확인 항목 |
| --- | --- |
| 프로젝트 | Unity 프로젝트가 깨끗한 환경에서 정상적으로 열리는지 확인 |
| 플레이 | 최소한의 2D 씬 실행, 입력 및 화면 전환 확인 |
| 빌드 | 플랫폼별 빌드 성공 여부와 산출물 생성 확인 |
| 설정 | 개발·스테이징·릴리스 환경별 설정 적용 확인 |
| 버전 | 앱 버전, 빌드 번호, Git 커밋 정보 반영 확인 |
| 배포 | 빌드 업로드, 다운로드 및 설치 과정 확인 |
| 업데이트 | 신규 버전 배포와 기존 버전의 업데이트 동작 확인 |
| 롤백 | 문제 발생 시 이전 안정 버전으로 복구 가능한지 확인 |

## 프로젝트 구조

```text
Assets/             Unity 에셋과 게임 코드
Packages/           Unity 패키지 설정
ProjectSettings/    Unity 프로젝트 설정
Builds/             로컬 빌드 결과물 (Git 제외)
Logs/               로컬 실행 및 빌드 로그 (Git 제외)
```

프로젝트가 확장되면 빌드 스크립트와 배포 설정은 다음과 같이 분리하는 것을 권장합니다.

```text
Assets/Editor/Build/    Unity Editor 빌드 스크립트
Config/                 환경별 설정 템플릿
Scripts/                로컬 빌드·배포 보조 스크립트
.github/workflows/      GitHub Actions 워크플로
```

## 개발 환경

- Unity: 프로젝트의 `ProjectSettings/ProjectVersion.txt` 기준
- Render Pipeline: 프로젝트 설정 기준
- 대상 플랫폼: 초기에는 개발 PC 환경을 기준으로 하며 필요에 따라 확장
- Git LFS: 대용량 바이너리 에셋을 추가할 경우 사용 권장

Unity Hub에서 저장소 폴더를 프로젝트로 추가한 뒤, 지정된 Unity 버전으로 실행합니다. 다른 Unity 버전으로 임의 업그레이드하면 프로젝트 설정이나 패키지 잠금 파일이 변경될 수 있으므로 주의해 주세요.

## 시작하기

1. 저장소를 클론합니다.
2. `ProjectSettings/ProjectVersion.txt`에서 Unity 버전을 확인합니다.
3. Unity Hub에서 프로젝트 루트 폴더를 추가합니다.
4. 프로젝트를 열고 기본 테스트 씬을 실행합니다.
5. 콘솔 오류가 없는지 확인한 뒤 대상 플랫폼으로 빌드합니다.

```bash
git clone <repository-url>
cd <repository-directory>
```

## 브랜치 운영

| 브랜치 | 용도 |
| --- | --- |
| `main` | 배포 가능한 안정 버전 |
| `develop` | 기능 및 파이프라인 통합 테스트 |
| `feature/*` | 개별 기능 또는 빌드 실험 |
| `release/*` | 배포 전 최종 검증 |
| `hotfix/*` | 배포 버전의 긴급 수정 |

작은 테스트 프로젝트인 동안에는 `main`과 `feature/*`만으로 시작하고, 자동 배포 단계가 늘어나면 `develop`과 `release/*`를 도입해도 됩니다.

## 버전 규칙

버전은 `MAJOR.MINOR.PATCH` 형식을 사용합니다.

- `MAJOR`: 배포 구조나 호환성이 크게 변경된 경우
- `MINOR`: 새로운 테스트 시나리오 또는 기능을 추가한 경우
- `PATCH`: 버그 수정이나 파이프라인 설정을 보완한 경우

배포 버전에는 Git 태그를 생성합니다.

```bash
git tag -a v0.1.0 -m "First build pipeline test"
git push origin v0.1.0
```

## 빌드 및 배포 흐름

1. 변경 사항을 브랜치에 반영합니다.
2. 기본 씬 실행 및 에디터 오류를 확인합니다.
3. 자동화된 검증과 플랫폼 빌드를 수행합니다.
4. 빌드 번호와 Git 커밋 정보를 기록합니다.
5. 스테이징 환경에 배포해 설치 및 실행을 확인합니다.
6. 검증이 끝난 산출물을 릴리스 환경에 배포합니다.
7. 문제가 발생하면 직전 안정 버전으로 롤백합니다.

## Git 관리 주의사항

다음 항목은 Git에 포함합니다.

- `Assets/`와 모든 `.meta` 파일
- `Packages/`
- `ProjectSettings/`
- 빌드 및 배포 자동화 설정

다음 항목은 `.gitignore`를 통해 제외합니다.

- `Library/`, `Temp/`, `Obj/`, `Logs/`, `UserSettings/`
- `Build/`, `Builds/`
- IDE가 생성한 사용자별 설정 파일
- 로컬 인증 정보와 환경별 비밀값

API 키, 배포 토큰, 인증서 비밀번호 등의 민감한 값은 저장소에 커밋하지 않습니다. CI/CD의 Secret 또는 환경변수로 관리합니다.

## 완료 기준

이 프로젝트의 핵심 완료 기준은 게임 콘텐츠의 양이 아니라 다음 사이클을 재현 가능하게 수행하는 것입니다.

> 코드 변경 → 검증 → 빌드 → 배포 → 설치·실행 확인 → 업데이트 또는 롤백

각 단계는 가능한 한 자동화하고, 실패했을 때 원인과 대상 버전을 추적할 수 있어야 합니다.
